Android Kiosk Tablets: App Preload, Lock Task Mode and MDM

The buyer’s question: do we need MDM, a DPC or custom firmware to ship a locked-down Android tablet?

Short answer: Android’s lock task mode keeps a tablet on your app, but only apps that a device policy controller (DPC) has allowlisted can run in it (Android lock task mode guide). So every kiosk project needs a DPC. It does not automatically need a full MDM, and it needs custom firmware only when something must exist before provisioning or below the app layer, such as a preinstalled system app, boot behaviour, drivers or the OTA client. Decide which layers you need before you ask for a quote.

The Android documentation describes both patterns for lock task mode: a single package that combines a kiosk and a mini DPC, or a DPC from an enterprise mobility management solution that launches your apps in lock task mode.

What the Android documentation says

  • Lock task mode runs on Android 5.0 or later. From Android 9.0 a DPC can start any app’s activity in lock task mode; before that, the app must start its own (lock task mode).
  • A DPC can end lock task mode remotely by removing the package from the allowlist. Do not start lock task mode while the device is locked, because the user might not be able to unlock it (same guide).
  • Fully managed devices suit dedicated uses such as check-in kiosks and digital signage. Device owner provisioning happens during out-of-box setup or on a factory-reset device (Android device management overview).

“App preload” means three different things

Ask every supplier which one they mean: the app is installed during provisioning by an MDM; the app is placed in the factory image; or the app is built into the firmware as a system app. They differ in when the app exists, what a factory reset leaves behind and how the app is updated. Do not assume; test it in scenario 4 below.

Three acceptance scenarios (plus one)

1. Cold boot straight into the kiosk

Test: power-cycle production-intent units repeatedly, including a power cut while the app is launching.
Pass: every start ends in the kiosk app with no setup wizard and no reachable launcher. Agree the number of cycles in writing.
Evidence: screen recording and device log.

2. Escape routes are closed

Test: try Home, Recents, notification shade, status bar, settings intents, a USB keyboard and USB debugging access. Android’s guide notes that in lock task mode users typically cannot see notifications, open non-allowlisted apps or return home unless the home screen is allowlisted.
Pass: no route reaches a non-allowlisted app; the agreed admin exit, if any, works.
Evidence: a signed test sheet listing each route tried.

3. Remote change without losing the lock

Test: from your MDM, push an app update and then an allowlist change.
Pass: the new app version runs in lock task mode; removing a package from the allowlist ends lock task mode for that app as documented; the screen never lands on an unintended app mid-update.
Evidence: MDM audit log plus screen recording.

4. Factory reset and re-provisioning

Test: reset a unit, then re-provision it.
Pass: you have a written list of which preloaded items survive the reset and how long re-provisioning takes.
Evidence: before/after app list and timing notes.
